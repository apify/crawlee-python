As we build our crawler, we may want to control how many tasks it performs at any given time. In other words, how many requests it makes to the web we are trying to scrape. Crawlee offers several options to fine-tune the number of parallel tasks, limit the number of requests per minute, and optimize scaling based on available system resources.

:::tip

All of these options are available across all crawlers provided by Crawlee. The examples on this page use the <ApiLink to="class/BeautifulSoupCrawler">`BeautifulSoupCrawler`</ApiLink>. You should also explore the <ApiLink to="class/ConcurrencySettings">`ConcurrencySettings`</ApiLink>.

:::

## Max tasks per minute

The `max_tasks_per_minute` setting in <ApiLink to="class/ConcurrencySettings">`ConcurrencySettings`</ApiLink> controls how many total tasks the crawler can process per minute. The tasks started over the last 60 seconds are counted, so the crawler may spend the whole limit early in the minute, as fast as its concurrency allows. It then waits until the oldest of those starts ages out of the window. By default, this is set to `Infinity`, meaning the crawler can run at full speed, limited only by `max_concurrency`. Use this option if you want to throttle your crawler to avoid overwhelming the target website with continuous requests.

## Minimum and maximum concurrency

The `min_concurrency` and `max_concurrency` options in the <ApiLink to="class/ConcurrencySettings">`ConcurrencySettings`</ApiLink> define the minimum and maximum number of parallel tasks that can run at any given time. By default, crawlers start with a single parallel task and gradually scale up to a maximum of concurrent requests.

:::caution Avoid setting minimum concurrency too high

If you set `min_concurrency` too high compared to the available system resources, the crawler may run very slowly or even crash. It is recommended to stick with the default value and let the crawler automatically adjust concurrency based on the system's available resources.

:::

## Desired concurrency

The `desired_concurrency` option in the <ApiLink to="class/ConcurrencySettings">`ConcurrencySettings`</ApiLink> specifies the initial number of parallel tasks to start with, assuming sufficient resources are available.

## Concurrency system

Every crawler runs its requests through an <ApiLink to="class/AutoscaledPool">`AutoscaledPool`</ApiLink>, and the pool asks a <ApiLink to="class/ConcurrencySystem">`ConcurrencySystem`</ApiLink> whether there is room for one more request. The system is what keeps `min_concurrency` requests running even while the machine is overloaded, starts further ones only while no [load signal](#load-signals) reports overload, and scales the budget up and down as the load changes. If any task raises an exception, the error is propagated and the pool is stopped.

The crawler builds its own system from the `ConcurrencySettings` described above. Build one yourself and pass it as `concurrency_system` to go beyond those settings, or to share a single budget between several crawlers that would otherwise each scale against the whole machine and oversubscribe it. The budget goes to whoever asks for it first, so a crawler that joins a saturated system late may have to wait. Browser crawlers default to a lower `desired_concurrency` than the rest, and a supplied system replaces that default too, so set it in the `ConcurrencySettings` you build the system from. Holding the instance also lets you retune `min_concurrency` and `max_concurrency` while the crawl runs. The lifecycle of such a system belongs to you, so keep it open until every crawler using it has finished.

## Load signals

Whether the machine counts as overloaded is decided by load signals. Four of them are built in: <ApiLink to="class/MemoryLoadSignal">`MemoryLoadSignal`</ApiLink>, <ApiLink to="class/EventLoopLoadSignal">`EventLoopLoadSignal`</ApiLink>, <ApiLink to="class/CpuLoadSignal">`CpuLoadSignal`</ApiLink> and <ApiLink to="class/StorageBackendLoadSignal">`StorageBackendLoadSignal`</ApiLink>, which watches the rate-limit errors of the storage backend. Each signal takes snapshots of its resource. A snapshot is overloaded when the resource is above its limit, such as `max_used_memory_ratio` or `max_event_loop_delay` in the <ApiLink to="class/Configuration">`Configuration`</ApiLink>. The signal is overloaded once the resource has spent more than `overloaded_ratio` of the recent time above its limit. If any signal is overloaded, the system is overloaded and the concurrency is held down.

You configure the signals through the `load_signals` option of the `ConcurrencySystem`, which takes <ApiLink to="class/LoadSignalsOptions">`LoadSignalsOptions`</ApiLink>. It has a field for each built-in signal that takes the options of that signal, such as <ApiLink to="class/EventLoopLoadSignalOptions">`EventLoopLoadSignalOptions`</ApiLink>. `False` switches a signal off, so it's neither collected nor evaluated, and the reported status shows it as not overloaded. :::info Signal names are the keys of the reported status

The `name` of a signal is the key of its verdict in the <ApiLink to="class/SystemInfo">`SystemInfo`</ApiLink>, so two signals can't share one, and the `ConcurrencySystem` raises a `ValueError` on a duplicate. Taking over a built-in name (`memory_info`, `event_loop_info`, `cpu_info` or `storage_backend_info`) therefore requires switching that built-in signal off. A custom signal under any other name is reported in `SystemInfo.load_signal_info`.

:::

The signals are evaluated over two windows of the `ConcurrencySystem`. `current_history`, 5 seconds by default, decides whether one more request may start. `snapshot_history`, 30 seconds by default, drives the scaling. Requests therefore start or wait as soon as the load changes, while the scaling stays stable. Both windows apply to every signal, and the signals keep as much history as the longer of them, so raising `snapshot_history` costs memory.

## Throughput concurrency system

The default <ApiLink to="class/ConcurrencySystem">`ConcurrencySystem`</ApiLink> adds tasks until CPU or memory runs out. When the target website is the bottleneck, more tasks stop paying off. The site answers more slowly, and the crawler finishes fewer pages while loading the site harder. The experimental <ApiLink to="class/ThroughputConcurrencySystem">`ThroughputConcurrencySystem`</ApiLink> steers by throughput instead. By Little's law, `N` tasks that each take `T` seconds finish `N / T` tasks per second, so more concurrency helps only while `T` grows slower than `N`. The system searches for the concurrency where throughput peaks. It reads throughput from windows of finished tasks and doubles the concurrency while that pays off. It then compares a level above and a level below the current concurrency, moves toward the better one, and holds once the two tie at the peak. It doesn't stay there for good. After each hold it measures the levels around the peak again, so even on a steady site the concurrency keeps moving within about 15% of it. The load signals of the default system, custom ones included, still apply.

Build it from your `ConcurrencySettings` and pass it to the crawler as `concurrency_system`, the same way as the shared system above. Crawlers sharing it get one search over all their tasks, which suits crawlers against the same site, and the budget goes to whoever asks first. Crawlers against different sites should set `per_consumer`. Each crawler then gets a search of its own, and `max_concurrency` is split between them fairly, so that one crawler can't starve the others. Each crawler keeps at least `min_concurrency`, so with many crawlers the total can go over `max_concurrency`. A crawler that hasn't asked for capacity for ten autoscale intervals, 100 seconds by default, and has nothing running is forgotten, and it starts its search over when it comes back.

The system works best on long-running crawls. It learns the peak from finished tasks, so the time it spends measuring pays off only over a long run.

Known limitations:

- Each step waits for its tasks to finish, so on slow pages the throughput system ramps up more slowly than the default one.
- Every finished task counts as work, so a site that answers fast with errors such as HTTP 429 looks like it can take more. To soften this, crawl through a <ApiLink to="class/ThrottlingRequestManager">`ThrottlingRequestManager`</ApiLink> with the site's domain in its list. It holds back the domain's requests after a 429, so the fast errors don't keep coming. For details, see [Request throttling](./request-throttling).
- A crawler that hits many hosts gets one search over all of them. It settles at the concurrency that suits the mix as a whole, which the slowest hosts tend to set. To give each site a peak of its own, crawl each with a crawler of its own on one system with `per_consumer` set.
- Stay with the default system when the machine is the bottleneck. When you need a fixed rate, use `max_tasks_per_minute` with the default system, since the throughput system only settles at whatever rate the limit lets through.

## Running under a resource limit

A crawler often gets less than the host machine has. A Docker container, a Kubernetes pod, a systemd slice and a Windows job object can each carry a limit of their own. Crawlee reads the limit that applies to the process and scales against it, with nothing to configure. The memory budget comes from the memory limit, the CPU load is measured against the cores the process may use, and the tightest limit wins when several of them apply. Without a limit, Crawlee falls back to the resources of the host machine. For the environment variables behind these options, see [Configuration](./configuration).

The budget is `available_memory_ratio` of the limit, 25% by default, and the crawler throttles once it uses `max_used_memory_ratio` of that budget, 90% by default. A container limited to 2 GB therefore throttles at around 460 MB. Both options live in the <ApiLink to="class/Configuration">`Configuration`</ApiLink>, together with `memory_mbytes` for sizing the budget in absolute terms. While the default ratio applies under a limit, Crawlee logs the resulting budget as a warning. Setting either `available_memory_ratio` or `memory_mbytes` silences the warning. Whatever the budget, the crawler also throttles once the memory charged against the limit goes above 97% of it, which includes memory used by other processes under the same limit.
