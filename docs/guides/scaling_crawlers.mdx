As we build our crawler, we may want to control how many tasks it performs at any given time. In other words, how many requests it makes to the web we are trying to scrape. Crawlee offers several options to fine-tune the number of parallel tasks, limit the number of requests per minute, and optimize scaling based on available system resources.

:::tip

All of these options are available across all crawlers provided by Crawlee. In this guide, we are using the <ApiLink to="class/BeautifulSoupCrawler">`BeautifulSoupCrawler`</ApiLink> as an example. You should also explore the <ApiLink to="class/ConcurrencySettings">`ConcurrencySettings`</ApiLink>.

:::

## Max tasks per minute

The `max_tasks_per_minute` setting in <ApiLink to="class/ConcurrencySettings">`ConcurrencySettings`</ApiLink> controls how many total tasks the crawler can process per minute. The tasks started over the last 60 seconds are counted, so the crawler may spend the whole limit early in the minute, as fast as its concurrency allows. It then waits until the oldest of those starts ages out of the window. By default, this is set to `Infinity`, meaning the crawler can run at full speed, limited only by `max_concurrency`. Use this option if you want to throttle your crawler to avoid overwhelming the target website with continuous requests.

## Minimum and maximum concurrency

The `min_concurrency` and `max_concurrency` options in the <ApiLink to="class/ConcurrencySettings">`ConcurrencySettings`</ApiLink> define the minimum and maximum number of parallel tasks that can run at any given time. By default, crawlers start with a single parallel task and gradually scale up to a maximum of concurrent requests.

:::caution Avoid setting minimum concurrency too high

If you set `min_concurrency` too high compared to the available system resources, the crawler may run very slowly or even crash. It is recommended to stick with the default value and let the crawler automatically adjust concurrency based on the system's available resources.

:::

## Desired concurrency

The `desired_concurrency` option in the <ApiLink to="class/ConcurrencySettings">`ConcurrencySettings`</ApiLink> specifies the initial number of parallel tasks to start with, assuming sufficient resources are available.

## Concurrency system

Every crawler runs its requests through an <ApiLink to="class/AutoscaledPool">`AutoscaledPool`</ApiLink>, and the pool asks a <ApiLink to="class/ConcurrencySystem">`ConcurrencySystem`</ApiLink> whether there is room for one more request. The system is what keeps `min_concurrency` requests running even while the machine is overloaded, starts further ones only while no [load signal](#load-signals) reports overload, and scales the budget up and down as the load changes. If any task raises an exception, the error is propagated and the pool is stopped.

The crawler builds its own system from the `ConcurrencySettings` described above. Build one yourself and pass it as `concurrency_system` to go beyond those settings, or to share a single budget between several crawlers that would otherwise each scale against the whole machine and oversubscribe it. The budget goes to whoever asks for it first, so a crawler that joins a saturated system late may have to wait. Browser crawlers default to a lower `desired_concurrency` than the rest, and a supplied system replaces that default too, so set it in the `ConcurrencySettings` you build the system from. Holding the instance also lets you retune `min_concurrency` and `max_concurrency` while the crawl runs. The lifecycle of such a system belongs to you, so keep it open until every crawler using it has finished.

## Load signals

Whether the machine counts as overloaded is decided by load signals. Four of them are built in: <ApiLink to="class/MemoryLoadSignal">`MemoryLoadSignal`</ApiLink>, <ApiLink to="class/EventLoopLoadSignal">`EventLoopLoadSignal`</ApiLink>, <ApiLink to="class/CpuLoadSignal">`CpuLoadSignal`</ApiLink> and <ApiLink to="class/StorageClientLoadSignal">`StorageClientLoadSignal`</ApiLink>, which watches the rate-limit errors of the storage client. Each signal takes snapshots of its resource. A snapshot is overloaded when the resource is above its limit, such as `max_used_memory_ratio` or `max_event_loop_delay` in the <ApiLink to="class/Configuration">`Configuration`</ApiLink>. The signal is overloaded once the resource has spent more than `overloaded_ratio` of the recent time above its limit. If any signal is overloaded, the system is overloaded and the concurrency is held down.

You configure the signals through the `load_signals` option of the `ConcurrencySystem`, which takes <ApiLink to="class/LoadSignalsOptions">`LoadSignalsOptions`</ApiLink>. It has a field for each built-in signal that takes the options of that signal, such as <ApiLink to="class/EventLoopLoadSignalOptions">`EventLoopLoadSignalOptions`</ApiLink>. `False` switches a signal off, so it's neither collected nor evaluated, and the reported status shows it as not overloaded. :::info Signal names are the keys of the reported status

The `name` of a signal is the key of its verdict in the <ApiLink to="class/SystemInfo">`SystemInfo`</ApiLink>, so two signals can't share one, and the `ConcurrencySystem` raises a `ValueError` on a duplicate. Taking over a built-in name (`memory_info`, `event_loop_info`, `cpu_info` or `storage_client_info`) therefore requires switching that built-in signal off. A custom signal under any other name is reported in `SystemInfo.load_signal_info`.

:::

The signals are evaluated over two windows of the `ConcurrencySystem`. `current_history`, 5 seconds by default, decides whether one more request may start. `snapshot_history`, 30 seconds by default, drives the scaling. Requests therefore start or wait as soon as the load changes, while the scaling stays stable. Both windows apply to every signal, and the signals keep as much history as the longer of them, so raising `snapshot_history` costs memory.

## Running under a resource limit

A crawler often gets less than the host machine has. A Docker container, a Kubernetes pod, a systemd slice and a Windows job object can each carry a limit of their own. Crawlee reads the limit that applies to the process and scales against it, with nothing to configure. The memory budget comes from the memory limit, the CPU load is measured against the cores the process may use, and the tightest limit wins when several of them apply. Without a limit, Crawlee falls back to the resources of the host machine.

The budget is `available_memory_ratio` of the limit, 25% by default, and the crawler throttles once it uses `max_used_memory_ratio` of that budget, 90% by default. A container limited to 2 GB therefore throttles at around 460 MB. Both options live in the <ApiLink to="class/Configuration">`Configuration`</ApiLink>, together with `memory_mbytes` for sizing the budget in absolute terms. While the default ratio applies under a limit, Crawlee logs the resulting budget as a warning. Setting either `available_memory_ratio` or `memory_mbytes` silences the warning. Whatever the budget, the crawler also throttles once the memory charged against the limit goes above 97% of it, which includes memory used by other processes under the same limit.
